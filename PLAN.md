# Plan — jmap-tui

How we build what [REQUIREMENTS.md](REQUIREMENTS.md) specifies. Architecture first, then the designs that make or break this project (rolling window, live sync, multi-account), then milestones, testing, and risks.

---

## 1. Architecture

Layered, with a hard rule: **the UI never talks to the network, and the sync layer never renders.** All cross-layer traffic flows through typed messages and a store snapshot.

```
┌──────────────────────────── terminal (Bubble Tea v2) ─────────────────────────────┐
│  ui/        sidebar · messagelist (rolling window) · preview · compose · modals   │
└──────────────▲─────────────────────────────────────────────────────▲──────────────┘
               │ user events (tea.Msg)                               │ view models + cmds
┌──────────────┴─────────────────────────────────────────────────────▲──────────────┐
│  app/       keymap router · pane focus · command dispatcher · toasts│store snapshot│
└──────────────▲─────────────────────────────────────────────────────┴──────────────┘
               │ queries / mutations (typed)          ▲ change notifications (tea.Msg)
┌──────────────┴──────────────────────────────────────┴─────────────────────────────┐
│  sync/     one engine per account (goroutine + hub)                               │
│   • EventSource listener  • /changes reconciliation  • query window manager       │
│   • in-memory store: Mailbox tree · Thread map · Email summaries · body LRU       │
└──────────────▲─────────────────────────────────────────────────────▲──────────────┘
               │ batched JMAP requests                                │ push events
┌──────────────┴─────────────────────────────────────────────────────┴──────────────┐
│  jmapclient/  thin layer over go-jmap: session, /query /get /set /changes,        │
│               upload/download blobs, EventSource, auth (keyring), retry/backoff   │
└───────────────────────────────────────────────────────────────────────────────────┘
```

**Dependency rule:** `ui` and `app` may import `sync` and `mail` only. `sync` may import `jmapclient` and `mail`. Nothing above `jmapclient` imports `go-jmap` — that is the swap point if the library disappoints.

### Provider seam

`mail.Provider` is defined in M0 and used by `sync` from day one:

```go
type Provider interface {
    Connect(ctx) error
    Mailboxes(ctx) ([]Mailbox, error)
    OpenQuery(ctx, QuerySpec) (QueryHandle, error)   // paged id stream
    FetchSummaries(ctx, ids) ([]EmailSummary, error)
    FetchBody(ctx, id) (EmailBody, error)
    Mutate(ctx, Mutation) error                       // flags/move/copy/destroy
    Send(ctx, Draft) (SendReceipt, error)
    Subscribe(ctx) (<-chan Change, func() error)      // live changes; nil ⇒ polling
}
```

JMAP implements it natively (storage-free). The interface exists to keep `sync` independent of the protocol client — the only implementation is JMAP, and the no-storage rule is unconditional (REQUIREMENTS FR-B4).

## 2. Data flow example — "user opens Inbox"

1. App start → config load → keyring auth → session discovery (M0).
2. `sync` engine per account: `Mailbox/query`+`get` → store. UI renders tree immediately (skeleton list).
3. Active mailbox = inbox → `Email/query` `{inMailbox: inboxId, collapseThreads: true, sort: [receivedAt desc], limit: 50, position: 0}`.
4. Response: `ids[0..49]`, `total`, `queryState`, `position`. Engine fetches summaries (`Email/get`, properties: `threadId, mailboxIds, keywords, from, subject, receivedAt, size, hasAttachment, preview`), stores, publishes snapshot.
5. UI renders 50 rows; user scrolls; at row 40 the window manager prefetches `position: 50` (§4.1) — user never waits.
6. EventSource fires `StateChange{Email: …}` → `/changes` → store patch → snapshot publish → list re-renders, scroll preserved by id.

## 3. In-memory store

- `Store` per account: `mailboxes` (tree), `emails` (id → summary), `threads` (id → email ids), plus *windows*: ordered id slices bound to (mailbox, query) pairs.
- **Bodies LRU**: ≤ 100 full bodies (default), evicted LRU; attachments fetched to temp only when saved, then deleted after handoff.
- Snapshots published via a versioned immutable struct; UI holds only the latest — no locks in render path (single-writer engine, copy-on-write maps or RWMutex with short critical sections).
- Eviction of *summaries* happens when a window is trimmed (§4.1) or mailbox switches (keep last N mailboxes warm).

## 4. The two hard problems

### 4.1 Rolling window pagination (endless scroll that never chugs)

State per open query: `{sort, filter, chunk=50, window: []id, anchorState: queryState, total}`.

- **Forward/backward extension:** when the cursor nears either edge of `window`, issue `Email/query` with `position` = windowEnd / `position` = max(0, windowStart−chunk) using the **same sort+filter**; merge id slices; fetch summaries for new ids only.
- **Deep-jump re-anchor (window > cap, default 2,000):** silently drop the far edge, `G`/`gg` issues a fresh query with `anchor` = nearest known id and `position` offset (JMAP supports anchor+offset); this keeps big mailboxes honest without page numbers.
- **Live changes while windowed:** `StateChange` → `Email/changes(sinceState)` → three cases:
  1. changed/destroyed ids **in window** → patch/evict, adjust `total`;
  2. server reports `cannotCalculateChanges` (rare) → full re-query preserving cursor id;
  3. new ids arrived → for *inbox-like sorted-by-date desc* views, new mail **slides in at top** with a subtle highlight (this is the delight moment); for other sorts, only update `total` and a "new below/above" hint.
- **Position preservation:** cursor and viewport track ids, not row indexes. On window mutation, re-derive row offsets; if the cursor's id was destroyed, land on its neighbour.
- **Debounce:** scroll-driven prefetches coalesce (80ms); re-anchors coalesce (300ms). Only one outstanding query per window — superseded results are discarded by monotonic request id.
- **Threads:** collapsed rows are thread representatives. Expanding runs `Thread/get` for the member ids (RFC 8621 §3 — the server returns them oldest-first) plus one `Email/get` for their summaries — window math is unaffected because thread expansion is a sub-list, not a window mutation. The same `Thread/get`, batched per view by `RefreshThreadSizes`, supplies the **member counts the list needs to mark which collapsed rows expand** (FR-D1 `▸`): the app asks whenever a row in view is unsized, the engine returns without a round trip once the view is warm, counts are pruned with the window, and a count is retired the moment a member can appear or vanish behind our back (new reply, destroy) so the next refresh relearns it. Three invariants keep the chevron honest (added 2026-09-26 after a wrong-row report): **one row per thread** in the window — a live reply supersedes its thread's existing row (and carries the cursor with it) instead of adding a second chevron beside it; **a chevron only when something renders beneath it**, so a single-message thread stays plain; and **the toggle targets the row the app rendered** (`ToggleThread(ctx, id)`), never the engine cursor, because the unified cursor is app-side (§4.3) and no engine cursor moves there.

### 4.2 Live sync engine

```
EventSource ──StateChange──▶ change hub ──▶ per-type /changes ──▶ store patch ──▶ tea.Cmd(snap)
     │                            │
     └─ reconnect w/ backoff      └─ mailbox counts via Mailbox/changes (FR-B6)
        (poll fallback at 60s)
```

- One EventSource per account. Parse `StateChange`; ignore types we don't track.
  - Transport note (M2): the stream client lives in `jmapclient/sse.go`, not go-jmap's `push` package — see the M2 milestone row for why. Ping is requested at 30s; a watchdog ends a stream silent past 75s so the reconnect loop replaces it.
- `/changes` results folded into the store; **all mutations made by the client itself also flow through `/changes` responses** (JMAP `/set` returns `newState`) — a single reconciliation path, no dual-write bugs.
- Optimistic mutations (FR-B7) write a pending-op overlay in the store; the next `/changes` or `/set` response clears or reverts it. The overlay machinery landed in M2 (`sync/overlay.go`): keyword/mailbox deltas, destroy-hides-row, re-apply when server updates race a pending op, confirm/revert paths — driven by M3 actions.
- Clock discipline: never trust client time for sync; state strings only.

### 4.3 Multi-account

- `sync.Hub` owns engines; each engine is a goroutine with its own store + EventSource.
- UI: active account pointer; `S` opens switcher (M6); unified view = read-only merge of selected accounts' inbox windows, interleaved by `receivedAt` with an owner colour bar; actions on unified rows dispatch to the owning engine (selection map account→ids).
- Failure isolation: one account's auth failure never blocks others; status line shows per-account state (FR-I5).
- M6 addendum (as shipped): the unified cursor is app-side — rows interleave, so no engine cursor moves — and tracks (account, id); the merge stamps `Row.Account` because JMAP ids are unique per account only (selection, body tracking, and action routing all qualify by owner). Entering unified forces each account's window to its inbox (remembered per account, reopened on exit) so the merge never clobbers independent state; leaving closes any unified search first. Engine snapshot versions are per-account, so the synthetic merged snapshot carries its own monotonic stamp. Triage batches group ids per owner; the move/copy/archive picker prompts once per owner over that owner's tree and dispatches a single undoable batch when the queue empties. Unified search fans one spec out per account (scope sentinel resolves to each account's inbox). Ops route through `engineFor`/`opOn`, which capture the owner engine at creation — a mid-flight account switch can never redirect an in-flight op.
- M6 body addendum (issue #1, fixed 2026-09-28): bodies follow the same app-side-cursor rule. `Engine.LoadBody` installs a fetched body only when it matches the engine's own cursor and `snapshotLocked` exposes it the same way — correct for a single account (the engine cursor *is* the list cursor) and wrong for unified, where no engine cursor ever moves: only each account's top row could ever install, and every row below it sat on `loading message…` forever, because the dropped fetch published nothing and the merged `BodyLoading` was driven by the still-pending request key. Unified loads now go through `Engine.BodyFor(ctx, id)` — LRU-first, network on miss, **no cursor gate and no publish** — and arrive as a `bodyMsg` keyed by the account-qualified row key, so a reply for a row the cursor already left is dropped instead of installed under the new one. The app keeps the installed body (`Model.uBody`/`uBodyKey`), which is what the merged snapshot carries as `Body` (attachment strip, save-attachment FR-E4); `BodyLoading` now means "the cursor row's body is neither displayed nor cached" — true in the very frame that creates the request, so the preview shows `loading message…` instead of a blank frame, and false the moment it installs. `bodyReq` stays purely the in-flight request key that dedupes rebuilds, drops stale replies, and is cleared (only when it is the request the preview waits on) by a failed load's `errMsg`. The single-account path, the cursor-scoped `Snapshot.Body`, and `setBodyLocked`'s invariant are untouched. `LoadBody` also now reads/writes the body LRU under the engine mutex (the cache has no lock of its own).
- M6 body-debounce addendum (FR-K4, 2026-10-04): body hydration is now debounced at the app layer (`Model.armBody`/`bodyDebounceMsg`, 120 ms) so holding a movement key passes any number of rows while issuing **one** fetch for the row it settles on, instead of one per row. The tick is generation-tagged (`Model.bodySeq`) and keyed by row; a firing tick is dropped when the cursor has moved on, and `bodyPending` dedupes re-arms from snapshot rebuilds so live updates cannot postpone the fetch. An LRU hit is never debounced: `Engine.CachedBody` probes the cache with no network, and the app loads a visited row immediately, so scrolling back through already-read mail paints at once. The debounce wraps both `applyUnified` (via `bodyMsg`) and the single-account `applyView` (via the engine's cursor-gated `LoadBody`); the engine still drops a fetch whose row is no longer the cursor if a move races the settlement. `bodyPending` is invalidated on account switch, unified enter/leave, and mailbox open.

- M6 persistence addendum (issue #2, 2026-09-28): the unified on/off flag is remembered in `prefs.toml` (key `unified`, FR-A5 amended — FR-J1: never `config.toml`) and written on every transition by `Model.saveUnifiedPref`, *after* enter/leave have repainted, because both repaints clear the status line (the write-on-toggle discipline of the pane layout, FR-I10; a failed write surfaces as a notice and never blocks the toggle; a session without a prefs store stays memory-only). `app.New` seeds `Model.unified` from it — **only with ≥2 enrolled accounts**, since `i` is a no-op otherwise and a seeded flag with one account would strand the reader in a view it cannot leave. A restored start cannot run `enterUnified` (no window is open yet), so the first-load branch of `applySnapshot` carries its semantics instead: each account's configured starting mailbox (FR-I8 `initial_mailbox`, else inbox) becomes `prevBox[acct]` and its **inbox** opens — the merge runs over real inboxes, and `leaveUnified` lands each account exactly where a non-unified session would have started. Nothing else about the session survives: no cursors, no open mailboxes, no search (FR-B4 keeps mail state in memory).

### 4.4 Fuzzy search fallback (M4 addendum)

Servers verify token-only search (PLAN §7: Stalwart matches whole words on every condition; partial words return nothing). The query bar **and every field of the advanced modal** therefore run two tiers, uniformly "contains-style":

1. **Fast path** — the debounced server query as typed. Non-zero results render with exact totals; full-word body search lives here.
2. **Fuzzy LIKE scan** — engaged automatically when the fast path returns zero results **and the spec has at least one text-ish field** (text/from/to/subject): the engine walks the scope newest-first (`Email/query` without the filter conditions, 500-id pages), fetches each batch's summaries, and matches client-side — every text word must appear in subject+from+to, subject words in the subject only, from words in From only, to words in To only (AND across fields and words). Exact fields re-apply natively over the summaries: keyword presence, attachment flag, exclusive after/before. Matches stream into the list with a header `scanning n/N`; `esc` or any new search supersedes the scan (generation counter). Only match ids are held — memory stays bounded, nothing is written to disk, and no local index persists across sessions (REQUIREMENTS non-goals intact).

Purely exact searches (keyword/attachment/dates only, no text-ish field) never scan: the server's zero is final and a scope walk would only repeat it (FR-K4). Scan views are flat (no thread expansion, no server-side jump positions); triage and live-change patches apply to scan matches as usual. Bodies are never scanned — summaries never carry them (full-word body search is the fast path's job).

Focus model (M4 addendum 2, user feedback): the query bar is a focused overlay, not a modal — `Enter` confirms the search **and** moves the cursor into the results list (an unchanged spec is not re-issued, so Enter never restarts an in-flight scan); while browsing results all pane keys apply; `/` re-focuses the bar; `Esc` (a global `ui.search_clear` binding) clears the search from anywhere the search view is open — bar or results — and is a no-op otherwise.

### 4.5 Contacts (M9 addendum)

The shape, in short:

- **Protocol.** RFC 9610 on hand-rolled method types inside `jmapclient` (go-jmap ships no contacts package — §9's wrapper rule). One batched initial fetch (`AddressBook/get` + `ContactCard/get` with a summary property subset), **no `ContactCard/query`** — sort and filter happen client-side (M4's token-only matching trap makes server-side substring search a dead end anyway), liveness via `{AddressBook,ContactCard}/changes` on the existing push stream. JSContact wire structs never leave `jmapclient`; `mail.Contact` above it.
- **Store.** Per-engine, parallel to the mail store: own state strings, own version, own **latest-wins channel** (`ContactSnapshot`) so the mail `Snapshot`/`applyView` path is untouched. **Lazy**: nothing loads until the composer or the contacts screen asks; a cold store skips every contact reconcile (poll and push alike) — zero cost for users who never open the feature. Reconcile folds `/changes` deltas (refetch changed ids, evict destroyed, `cannotCalculateChanges` ⇒ wholesale reload). Mutations are **confirmed-then-patch**: one batched `ContactCard/set`, then the touched ids refetch and the response's `newState` folds into the store — no optimistic overlay, no dual-write.
- **Seam.** `mail.ContactProvider`, a separate optional interface (type-asserted by the engine, capability-gated on `urn:ietf:params:jmap:contacts`) — contacts are not mail, and a JMAP server may not advertise them at all. Absence degrades to hidden features (FR-A6, FR-L6).
- **UI.** The full-screen view is a pointer-field overlay like the composer (`contactsState`), owning its own key loop below every modal; the form modal is the advanced-search pattern; the suggestion popup lives inside the composer and intercepts its keys only while it shows a pick; `ctrl+g` reuses the picker (`pickerContactQuick`) so it layers over the composer exactly like the identity picker. Merged suggestions dedupe by email across every supporting account.

## 5. UI design notes (minimal & elegant)

- **Type:** rows are single-height, generous cell padding, muted secondary text; unread = bold + accent dot; selection = soft background wash, not a harsh inverse.
- **Color:** exactly one accent; semantic muted/success/danger; everything else terminal-adaptive. Lipgloss v2 `AdaptiveColor`; two themes (dark, light) + `--theme` flag; user theme file [FUTURE].
- **Chrome:** no full-screen borders by default; panes separated by whitespace and a hairline vertical rule; header = mailbox breadcrumb; footer = status line (FR-I5).
- **Motion:** none gratuitous; the only "animation" is the new-mail slide-in highlight (4.1) and toast fade.
- Bubbles used: `textinput` (search, compose headers), `textarea` (compose body), `viewport` (preview), `filepicker` (attachments), `spinner`, `help`, `table`-like custom list (custom — Bubbles `list` is too opinionated for rolling windows).

### 6.2 M10 design — server auto-config (planned 2026-09-28, landed 2026-09-28)

Kept as the design record. As landed: `Discoverer` carries a `Timeout`
field (the budget `min(opts.Timeout, 10s)` from the paragraph below lives
on the struct, so `New` can cap it once), `Prober.Probe` returns the URL
the probe *finished on* and `Discover` decides what that means for
`session_url`, and the edit-mode rule below — "discovery only runs when
the field is empty" — is the wording that survived the interview: an edit
shows the field, so discovery runs only when the user clears it (the test
list's "edit mode never discovers" was the discarded half of that
conversation).

**Goal:** the wizard's form becomes *email address + password*. On Enter the wizard probes DNS and discovers the JMAP server URL; if nothing is found, the **Server URL field appears** (focused) for manual entry. Scope decisions were interviewed 2026-09-28: probe chain = **SRV + domain fallback**, trigger = **final Enter**, verification = **unauthenticated HTTP probe**, landing = **now** (after the v0.1.0 tag).

**Standard:** RFC 8620 §2.2 — a JMAP host for `example.com` SHOULD publish `_jmap._tcp.example.com` giving hostname + port (usually 443); the session resource is then `https://${hostname}[:${port}]/.well-known/jmap` (following redirects), and a client MAY use the domain part of an email-shaped username to attempt discovery.

**Probe chain** (first verified hit wins):

1. `LookupSRV(ctx, "jmap", "tcp", <domain>)` → `https://<target>[:port]` (port 443 omitted, trailing dot trimmed) → probe `GET <base>/.well-known/jmap`.
2. Fallback: probe `https://<domain>/.well-known/jmap` (catches a bare Stalwart domain with no SRV record).
3. Both fail → error naming both attempts → Server URL field revealed.

**Probe acceptance:** status **200 with session-looking JSON** (`capabilities` or `apiUrl`), or **401/403** (right host, auth required — the credential test that follows does the real auth). Redirects followed. A **cross-origin** final URL (jmapclient refuses cross-origin redirects, `client.go` `refuseCrossOriginRedirects`) is recorded as `session_url` alongside the candidate base in `url` — the config already has the key and the client's trust anchor already includes `SessionURL`. Every result passes `config.ValidateServerURL` before it leaves the package. The probe never carries credentials.

**New package `internal/discover`:**

```go
type SRVResolver interface { LookupSRV(ctx, service, proto, name string) (string, []*net.SRV, error) }
type Prober interface { Probe(ctx context.Context, baseURL string) (SessionURL string, err error) }
type Discoverer struct { Lookup SRVResolver; Prober Prober; Scheme string } // Scheme http only for loopback tests
func (d *Discoverer) Discover(ctx context.Context, email string) (Result, error)
type Result struct { URL, SessionURL, Source string } // Source: "srv" | "domain"
```

Zero new dependencies (stdlib `net.Resolver` + `net/http`); own timeout (min(opts.Timeout, 10s)); errors wrapped `%w`, never echo anything secret. Domain extraction: text after the last `@`, lowercased, trailing dot stripped; no `@`/empty domain → actionable error.

### 6.3 Styled HTML rendering — design record (landed 2026-09-29)

Kept as the design record for FR-E2's second half: HTML bodies are no
longer flattened to plain text.

**Pipeline.** `mailtext.HTMLToMarkdown` shares the existing DOM walker
with `HTMLToText` and differs only at the emission points: ATX headings,
`*`/`**` emphasis, `- `/`1. ` lists (four-space nesting), `> ` quotes,
`---` rules, fenced code, pipe tables, and text escaped so sender content
cannot smuggle structure (`&` round-trips as `&amp;` because the renderer
runs `html.UnescapeString` over text nodes). The output is `Sanitize`d
before it leaves the package, so the markdown source carries no control
bytes at all. `internal/ui.RenderBody` then styles it with
`charm.land/glamour/v2` — Glow's engine — using a stylesheet derived from
`Palette`: accent on headings/links/code, muted on quotes and footnotes,
body colour for text, **no margins** (every column belongs to the pane),
no borders, no backgrounds. `WithPreservedNewLines` keeps the `<br>` a
hard break instead of letting a paragraph rejoin it.

**Where it sits.** The engine caches the *width-independent* markdown
(`BodyView{Text, Styled}`) and keeps `EmailBody.Text` as the plain text a
reply quotes — the two readers want different things and must never share
a string. The render happens **once**, in `app.setBody`; the result is
width-independent (glamour is asked not to wrap) and every resize then
re-wraps it with `ansi.Wrap`, exactly like a plain body, so the render
never sits on the resize path. The frame boundary (`ui/sanitizeState`)
moved to `SanitizeStyled`, which passes well-formed CSI SGR and drops
every other escape whole — including OSC hyperlinks, whose payload the
reader already sees as text.

**Why glamour does not wrap.** Its wrapping pads every line to the wrap
width with *one styled space per column*, and the padding writer
re-parses ANSI for each: measured at ~10 ms/KB, four times the rest of
the render put together, and it made every resize re-render. With
`WithWordWrap(0)` the padding writer never fires, the output no longer
depends on a width, and the whole pipeline costs ~1.6 ms/KB — paid once
per body. The visible trade-off is that tables size to their content
rather than the pane, so a table wider than the pane is word-wrapped by
`ansi.Wrap` like any other long line (the pre-existing plain-text
behaviour).

**Degradation.** Glamour error or a source past `maxStyledBodyBytes`
(64 KB ≈ a 100 ms frame) → the sanitized markdown source, readable and
never blank; `text/plain` bodies bypass the renderer entirely.
`trimTrailingPad` then drops whatever trailing space the renderer still
leaves (table cell padding, an empty styled run) — invisible without a
background colour, but the viewport carries every line in memory on
every frame. If profiling ever shows the one-time render janking a slow
machine, the upgrade is a stale-discarded `tea.Cmd`, the same shape the
body fetch already uses.

**Scope boundary.** This is not HTML/CSS rendering: no layout engine, no
CSS cascade, no images, no remote content (REQUIREMENTS §4). Layout
tables are recognised and *not* turned into grids.

## 8. Testing strategy

- **mockjmap:** deterministic in-process JMAP server (httptest) with scriptable event injection — drives sync engine tests without network. Contact fixtures journal `ContactCard`/`AddressBook` changes and serve path patches; `DisableContacts()` exercises the FR-L6 gate.
- **Golden tests:** bubbletea v2 golden files for list/preview/compose/modals/wizard/contacts at 3 terminal sizes (120×40, 99×35, 59×25) × dark/light (the wizard frames cover the add form with the Server URL hidden, the same form with it revealed, finding server, connection failure, mailbox pick, keyring failure, and the saved summary; contacts cover the screen at all three sizes, the form modal, and the suggestion popup).
